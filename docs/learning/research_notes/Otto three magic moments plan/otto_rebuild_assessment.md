# Otto rebuild assessment: keep, adapt or rebuild for the three magic moments

Research notes, read from the repository only, at commit `607e37f4` (2026-11-05). No web sources. Paths are repo-relative and cite `path:line`. The three moments assessed: (1) photo of a meal → full recipe (ingredients with amounts, steps, servings in units like slices, nutrition per serving), saved; (2) Otto AI plans the whole week (breakfast, lunch, dinner, snacks) as a free per-day list with optional labels, editable and swappable; (3) Otto AI can do anything the user can do by hand, by talking or typing.

Docs read first and treated as current: `CLAUDE.md`, `docs/architecture/C4.md`, `ERD.md`, `EDGE_FUNCTIONS.md` (all "Status: current · verified at `0cbfaa9f` · 2026-11-04"), ADR-0005/0006/0008/0011/0013/0014, `docs/tickets/PRODUCT_ROADMAP.md`, `docs/tickets/DESIGN_ROADMAP.md` (both "planning only"), `docs/product/MAGIC_MOMENTS_V2.md` ("planning only, nothing built"), `docs/learning/research_notes/Otto AI agent research/otto_actions_and_ai_today.md` (read at `d03c6fc1`). Key claims from those docs were spot-checked against code.

## 1. Keep / adapt / rebuild matrix by area

### Takeaway
"From scratch" is not warranted for most of the stack: the shell, auth, purchases, Supabase + RLS data layer, the nutrition engine, the design system and the test/CI setup are sound and should be kept. The three moments need **new** pieces (a dish-reconstruction vision mode, a serving-unit/yield model, a plan-item model with label and order, an agent edge function with tools, image generation, a pre-account scan path) and **adaptation** of the recipe, planner and chat layers. Only the chat backend (recipe-builder JSON, no tools) and the vision prompt are true rebuilds.

### Inferences
- A literal from-scratch rewrite would throw away the three most expensive, most tested assets (nutrition engine + golden corpus, the 795-recipe canonical catalogue with per-line grams and USDA keys, the RLS model) for no gain on the moments. The right frame is "new core features on a kept platform".
- The `*.queries.ts` one-function-per-action pattern makes moment 3 mostly a cataloguing exercise on the client side; the hard part is server-side (agent loop, tool auth, undo log), plus moving kv data to tables.

### Gaps
- Whether production sets `REQUIRE_CLUB=on` and `EXPO_PUBLIC_USE_OTTO_RECIPES=true`: production builds use EAS server-side environment `production` — [eas.json:16-17](eas.json) — and only `.env.development:9` sets the catalogue flag to `true`; the code default is OFF — [canonical.transform.ts:20-23](src/features/recipes/canonical.transform.ts). If the flag is off in production, the shipped app serves TheMealDB, not the 795-recipe catalogue.
- Cook mode, household and ShoppingScreen were judged from the otto_actions note and line counts, not read line by line.

## 2. Recipe model: servings/yield, serving units, nutrition per serving, forking

### Takeaway
Servings are a bare integer everywhere except `favorites.servings` (text); there is no yield unit, no "slice/piece/bowl" concept, no cook times, and catalogue recipes cannot be edited or forked. Nutrition **is** per serving (`per: "serving"`) and point-valued with a confidence label, not the `~` range ADR-0013 promises.

### Cited Findings
- **Servings types are mixed:** `recipes.servings integer`, `favorites.servings text` ("display text"), canonical `servings: number` — [ERD.md](docs/architecture/ERD.md); generated types confirm `servings: string | null` on favorites and `number | null` on recipes — [src/types/database.ts:33, 278](src/types/database.ts); canonical schema `servings: z.number().nullish()` — [canonical.transform.ts:54](src/features/recipes/canonical.transform.ts). All 795 catalogue records have numeric `servings` and **0** have any time field (node count over `supabase/otto-recipes/canonical/recipes.json`; also [MAGIC_MOMENTS_V2.md](docs/product/MAGIC_MOMENTS_V2.md) "`canonical` has no time field").
- **No serving unit exists:** a grep for `slice`, `servingUnit`, `serving_unit`, `yield` across `src` finds only `Array.slice` calls and comments — no data field. Model output schema has `servings: integer | null` only — [generate-recipe/index.ts:50](supabase/functions/generate-recipe/index.ts); server clamps to default 4, max 24 — [generate-recipe/index.ts:145](supabase/functions/generate-recipe/index.ts).
- **Unknown yield defaults to 4:** detail uses `recipe.servings || 4` as the base — [RecipeDetailScreen.tsx:99](src/features/recipes/RecipeDetailScreen.tsx); new manual drafts use `DEFAULT_SERVINGS` — [draft.ts:79](src/features/import/draft.ts). For TheMealDB seeds the engine overrides servings with curated `recipeFacts.json` judgements because "a flat default of 4 divided '2kg Shredded Meat' into a 1200 kcal/serving card" — [compute.ts:30-48, 78-80](src/features/nutrition/engine/compute.ts).
- **Every recipe opens at 1 serving** (founder call) and the stepper scales by `servings / baseServings` — [RecipeDetailScreen.tsx:66-69, 99-100](src/features/recipes/RecipeDetailScreen.tsx).
- **Nutrition is per serving:** `NutritionResultSchema` has `kcal`, macros, `basis_grams`, `per: z.literal("serving")`, `confidence: high|medium|low`, `basis: measured|estimated`, `doubt` — [src/features/nutrition/engine/schemas.ts:13-29](src/features/nutrition/engine/schemas.ts). `NutritionCard` derives `perServing` macros and scales them — [NutritionCard.tsx:63-91](src/features/nutrition/components/NutritionCard.tsx). User recipes store the per-serving figure at save — [import.queries.ts:216-232](src/features/import/import.queries.ts). Seed figures are precomputed in `seed_nutrition`, which "no client code reads … today" — [ERD.md](docs/architecture/ERD.md).
- **No range:** the schema has a single `kcal` number; ranges exist only in tests (`within(out, lo, hi)`) — [golden.test.mjs:10-13](src/features/nutrition/engine/golden.test.mjs). ADR-0013 decision 1 asks for "`~` with a range" — [docs/adr/0013-…md](docs/adr/0013-magic-moments-snap-any-dish-and-otto-plans-your-week.md).
- **Per-line grams exist** on the catalogue path ("canonical TOTAL grams for this line — the same weight seed_nutrition was computed from") — [recipe.types.ts:14-19](src/features/recipes/recipe.types.ts); user recipes get grams at save via `ingredientsWithGrams` — [import.queries.ts:230](src/features/import/import.queries.ts).
- **No fork/edit from catalogue:** the Edit affordance renders only for user recipes ("User's own recipe (id "u-…") — edit affordance") — [RecipeDetailScreen.tsx:228-233](src/features/recipes/RecipeDetailScreen.tsx); `isSeed = !isUserRecipeRef(recipeId)` — [RecipeDetailScreen.tsx:101](src/features/recipes/RecipeDetailScreen.tsx); `parseEditId` accepts only `u-N`/numeric user ids — [draft.ts:62-65](src/features/import/draft.ts). Saving a catalogue recipe writes a `favorites` snapshot (title, image, cook_time, servings text, category), not a copy — [ERD.md](docs/architecture/ERD.md). `recipes` has no `forked_from` column — [ERD.md](docs/architecture/ERD.md).
- **Two id systems:** seed ids are numeric strings ("52772", Otto originals 900001+) and user ids are `"u-12"`; `favorites.recipe_id` is **integer**, `plan_entries.recipe_id` is **text**; no FKs — [ERD.md](docs/architecture/ERD.md), [plan.types.ts:7-9](src/features/planner/plan.types.ts).
- Stale comment: `Recipe.source` comment lists `'themealdb' | 'manual' | 'imported'` — [recipe.types.ts:22-23](src/features/recipes/recipe.types.ts) — but `source: 'otto'` is written by chat/vision — [draft.ts:117-118](src/features/import/draft.ts), [generate-recipe/index.ts:374](supabase/functions/generate-recipe/index.ts).

### Inferences
- "Servings in units like slices" needs a new yield model, e.g. `yield: { count: number, unit: 'serving'|'slice'|'piece'|'bowl'|…, label?: string }` on both canonical and `recipes`, with nutrition `per` widened from the literal `"serving"` to the yield unit. The engine's per-serving divide (`perServing = max(1, facts.servings || servings || 1)`, `compute.ts:80`) already works for any count; only labels and schemas change.
- A nutrition range can be derived from data the engine already produces (`doubt`, `confidence`, `basis`), so "`~` with a range" is an adaptation of the output schema and card, not a new engine. The golden corpus protects against regressions while doing it.
- Forking a catalogue recipe into `recipes` (copy canonical → user row with lineage) is required for moment 1 ("closest catalogue recipe · Make my own"), for moment 2 (agent tweaks a catalogue dish), and for moment 3 ("make this vegetarian and save it").

### Gaps
- How `recipeFacts.json` servings interact with the 795 canonical records (which carry their own servings) on the ON path was not traced.
- Whether any UI surfaces `confidence`/`doubt` to users today was not checked.

## 3. Planner: can plan entries be non-recipe items or labelled?

### Takeaway
Partly. A plan day is already a free list (no breakfast/lunch/dinner slots), and a row with `recipe_id = null` plus `note` is allowed ("null for a note"), but there is no `label`, no explicit order, no item type, and the UI's only tag is the overloaded `note = 'leftovers'`. The week is a rolling 7-day window from today and swap is non-atomic, which a whole-week AI commit will stress.

### Cited Findings
- `plan_entries`: `day date`, `recipe_id text` (`"52772"` seed, `"u-12"` user, **null = note-only row**), `title`, `image`, `category`, `note`, `cooked` — [ERD.md](docs/architecture/ERD.md), migration `20260721090003_plan_entries.sql:3-14`.
- Client input type requires a `recipeId: string` — [src/features/planner/plan.types.ts:10-17](src/features/planner/plan.types.ts), so the app never writes a note-only item although the schema allows it.
- Order within a day is insertion time: `.order('created_at', { ascending: true })` — [plan.queries.ts:23](src/features/planner/plan.queries.ts). No position column — [ERD.md](docs/architecture/ERD.md).
- Leftovers are tagged by setting `note` to `'leftovers'` — [PlanScreen.tsx:109-113, 208](src/features/planner/PlanScreen.tsx).
- Week is `weekDays()` computed per mount, list fetched for `days[0].key..days[6].key` — [usePlan.ts:56-64](src/features/planner/usePlan.ts).
- Swap = `removePlanEntry` then `addPlanEntry` (two calls, not atomic) — [usePlan.ts:99-103](src/features/planner/usePlan.ts) (per otto_actions note). Roadmap plans an atomic `put_in_plan` RPC and replaces the `meal` column idea with optional `label` — [PRODUCT_ROADMAP.md:86](docs/tickets/PRODUCT_ROADMAP.md), [ADR-0013](docs/adr/0013-magic-moments-snap-any-dish-and-otto-plans-your-week.md) decision 3.
- Plan entries are household-readable (RLS) — [ERD.md](docs/architecture/ERD.md).
- Shopping list is derived from the week's recipes — `plan.queries.ts:56-116`, `shoppingList.ts` (otto_actions note).

### Inferences
- Migration for moment 2 is additive: `label text null` (breakfast/lunch/dinner/snack/custom), `position int`, `kind` (recipe | free text, e.g. "yogurt and fruit"), `servings`/`yield` override per item, `source` ('otto' | 'user') and an `agent_action_id` for undo. Existing rows map cleanly (label null, position by created_at, kind from recipe_id null-ness).
- "Plan the whole week including snacks" means ~21-28 items per week; a batch commit RPC (preview → one transaction) is needed, both for atomicity and for one Undo.
- The catalogue lacks cook times (0 of 795) and meal-type tags beyond `category`, so "breakfast" or "30 minutes" filtering needs data work (R0.14) before `plan_week` is trustworthy.

### Gaps
- Whether `category` values in the catalogue can identify breakfast/snack dishes reliably was not measured (the painted art set has `cat-breakfast.webp`, suggesting a Breakfast category exists).

## 4. Vision path: what changes for dish → recipe

### Takeaway
The existing vision mode is a faithful **transcriber of recipe pages** that is told not to invent anything; moment 1 needs the opposite (identify a cooked dish and *reconstruct* a plausible recipe), so the prompt, schema and flow are a rebuild, while the transport (base64 image, size/mime check, strict JSON schema, review-first editor, on-device nutrition at save) is reusable.

### Cited Findings
- Instruction: "This photo shows a recipe — a cookbook page, a handwritten card, or a screenshot. Transcribe it faithfully … don't invent, pad, or 'improve' anything the photo doesn't show … If the image isn't a readable recipe … set is_possible to false" — [supabase/functions/generate-recipe/imageMode.ts:27-33](supabase/functions/generate-recipe/imageMode.ts). A photo of a plate would therefore be declined (422).
- Vision uses `gpt-5.1`, `reasoning_effort` omitted, same SCHEMA as one-shot — [generate-recipe/index.ts:15, 350-374](supabase/functions/generate-recipe/index.ts). SCHEMA has only `is_possible, decline_reason, title, servings, category, area, ingredients[{measure,name}], steps` — [generate-recipe/index.ts:42-63](supabase/functions/generate-recipe/index.ts): no detected components, confidence, portion estimate, questions or catalogue match.
- Response always `image: null` — [generate-recipe/index.ts:374](supabase/functions/generate-recipe/index.ts); the user's photo is not kept as the recipe image by this path. Upload to `recipe-photos/<uid>/<uuid>` exists separately — [import.queries.ts:140-168](src/features/import/import.queries.ts) (per otto_actions note); bucket is **public** — [ERD.md](docs/architecture/ERD.md).
- Size cap: base64 ≤10,000,000 chars, jpeg/png/webp — [EDGE_FUNCTIONS.md](docs/architecture/EDGE_FUNCTIONS.md) (`imageMode.ts:8-23`).
- Every AI endpoint requires a user JWT before anything else — order "preflight → method → JWT → rate limit → club gate" — [EDGE_FUNCTIONS.md](docs/architecture/EDGE_FUNCTIONS.md); rate limiter is an isolate-local `Map` that resets on cold start — `_shared/http.ts:96-110`.
- ADR-0013 design: editable chips "Otto sees: rice, black beans…", at most 2 questions, catalogue match first, nutrition by the on-device engine, user's photo as image, photo stripped of location and not kept on the server, 3 scans per device before an account checked with DeviceCheck/App Attest — [MAGIC_MOMENTS_V2.md](docs/product/MAGIC_MOMENTS_V2.md), [ADR-0013](docs/adr/0013-magic-moments-snap-any-dish-and-otto-plans-your-week.md). No DeviceCheck/App Attest code exists (grep empty).
- Roadmap requires a weighed calibration set before shipping — [PRODUCT_ROADMAP.md:88, 164](docs/tickets/PRODUCT_ROADMAP.md).

### Inferences
- New contract, likely a separate mode or function (`scan-dish`): step 1 identify (dish name, components with estimated grams and confidence, cooking-fat guess, yield/portion estimate, up to 2 clarifying questions, catalogue search terms); step 2 reconstruct (ingredients weight-first, steps, yield with unit). Keep the honesty rule that the model never outputs calories.
- Catalogue match needs a search over 795 records by dish name/ingredients (text search or embeddings); nothing like it exists (Discover uses category/area filters and title search — `recipe.queries.ts:55-323`).
- Pre-account scanning conflicts with JWT-first edge functions; options are Supabase anonymous auth (then claim on sign-up) or a device-attested unauthenticated endpoint. Either is new server code with abuse risk.
- Storing the user's photo as the recipe image collides with "not kept on the server" unless the photo is uploaded only on Save (after account), and the public bucket should be reconsidered for user dish photos.

### Gaps
- No accuracy data for dish reconstruction exists in the repo beyond the referenced research note `photo_nutrition.md` (not re-read here).

## 5. Sizing: fresh build vs refactor, blockers, data migration

### Takeaway
Roughly: fresh builds are the scan-dish endpoint + flow, the agent edge function + tool layer + action log, image generation, the pre-account scan path, and the week-plan preview/commit; refactors are the recipe yield model, plan schema, prefs/shopping/consent to the server, chat UI to agent cards, tab bar. The biggest blockers are (a) no tool-calling or server-side context for the AI, (b) data the agent needs living on the device, (c) no yield unit and no cook times in the data, and (d) the gate/JWT model versus scanning before an account.

### Cited Findings
- No function calling exists; chat gets only the last 12 turns and no prefs/plan/household context — [otto_actions_and_ai_today.md §2](docs/learning/research_notes/Otto%20AI%20agent%20research/otto_actions_and_ai_today.md) (`generate-recipe/index.ts:299-335`, `ChatScreen.tsx:81`).
- Candidate tool catalogue already maps to existing query functions (plan add/remove/swap/setCooked, saved toggle, recipe create/update/delete, imports, household list ops) — same note, Inferences; device-only actions "cannot be executed by a server-side agent today" — same note.
- Roadmap's Foundations bundle the same prerequisites: prefs with allergies on the account, atomic `put_in_plan`, server-side shopping list, Postgres rate limiter, `requireClub` always on, `agent_actions` table, account-level consent; cook-time estimates; image pipeline; vision reconstruct mode with calibration; DeviceCheck scan limit; `src/shared/actions` catalogue with a test — [PRODUCT_ROADMAP.md:79-89](docs/tickets/PRODUCT_ROADMAP.md). None of `app_events`, `agent_actions`, DeviceCheck exist in code (grep empty).
- Critical path: "preferences on the account → week builder" and "the vision calibration set → Snap any dish" are the long poles — [PRODUCT_ROADMAP.md:164](docs/tickets/PRODUCT_ROADMAP.md).
- Data shapes needing migration: text `user_id` without FK on favorites/recipes/plan_entries/shares; `favorites.recipe_id integer` vs `plan_entries.recipe_id text`; `favorites` stores text snapshots (`servings text`, `cook_time text`); `recipe_shares.recipe_id` has no FK — [ERD.md](docs/architecture/ERD.md).
- Device-only data (journal photos as local file URIs, chats, personal shopping state, prefs, ratings, consent) — [src/shared/storage.ts:8-24](src/shared/storage.ts), [useJournal.ts:7-57](src/features/journal/useJournal.ts) (per otto_actions note). Cache is busted on every app version — [ADR-0011](docs/adr/0011-offline-persist-the-query-cache-never-sync-mutations.md).

### Inferences
- **Fresh build (new code):** `scan-dish` edge function + calibration harness; scan UI (camera, chips, questions, match card); pre-account scan identity (anonymous auth or attested device) and claim-on-sign-up; `otto-agent` edge function with tool registry, step cap, per-tool risk/confirm, `agent_actions` undo log; agent cards in chat; `plan_week` planner logic (catalogue-first, allergy filter in code, preview, batch commit); image generation + Storage + "AI image" tag; catalogue search/match.
- **Refactor/adapt:** recipe yield model across canonical, `recipes`, engine output, scale display, editor; nutrition range in schema/card; plan_entries schema + `usePlan` + PlanScreen; prefs/shopping/consent to tables with hooks; fork-from-catalogue; route gate; tab bar; chat transport reuse.
- **Migration of existing users (additive, server-side):** add columns with nulls/defaults (plan label/position/kind; recipe yield unit defaulting to "serving"; recipe lineage); backfill `position` from `created_at`; convert text `user_id` to uuid FK (needs a check that all values are valid uids; orphan cleanup); optionally convert favorites to text recipe ids. **Client-side one-time upload** on first launch of the new version for kv data that should survive (prefs, personal shopping state, consent, possibly chats and journal photos to Storage) — this can only run on each user's phone, and data on phones that never update is lost; the cache bust per version (ADR-0011) does not affect kv but means the first launch is online-dependent.
- Recipe nutrition stored at save (`recipes.nutrition`) would need recomputation if the output schema gains ranges or yield units; the engine is deterministic so a batch recompute is safe, but `resolved_ingredients` hits depend on the server cache.

### Gaps
- Number of existing users/rows is not in the repo (needs the live database), so migration cost by volume is unknown.
- Agent cost per request and image cost are estimates only in docs ("a few cents", "$0.002–0.02 per scan") — [ADR-0014](docs/adr/0014-ai-recipe-images-are-photorealistic-and-tagged.md), [MAGIC_MOMENTS_V2.md](docs/product/MAGIC_MOMENTS_V2.md).

## 6. Code that contradicts the ADRs, and the riskiest parts

### Takeaway
The ADRs from 2026-11-04/05 describe a future the code does not implement yet (expected: they are marked planning), but a few are real contradictions in shipped behaviour: the server does not enforce the hard paywall by default, AI consent is per device, the vision mode refuses exactly the photos moment 1 needs, and nutrition has no range. The riskiest parts are photo accuracy, the agent's write authority, the pre-account scan endpoint, and data migration off the device.

### Cited Findings
**Contradictions or not-yet-built against ADRs**
- ADR-0005 (hard paywall) vs server: `requireClub` is off unless `REQUIRE_CLUB` is exactly `on` — [EDGE_FUNCTIONS.md](docs/architecture/EDGE_FUNCTIONS.md) (`_shared/http.ts:43-94`); `canonicalize` has no user auth (1000/h per isolate) — same doc, flagged as a risk.
- ADR-0006 (consent before AI): consent is stored per device in kv `aiConsentOpenAI`, not per account — [ADR-0006](docs/adr/0006-ai-runs-on-openai-behind-supabase-edge-functions-with-per-pr.md); stale comments still name Anthropic/Claude, e.g. `ChatScreen.tsx:121`, `AddSheet.tsx:126`, `nutrition.queries.ts:60` — [EDGE_FUNCTIONS.md](docs/architecture/EDGE_FUNCTIONS.md) open question 10; the engine header still mentions "Claude-as-matcher" — [compute.ts:3](src/features/nutrition/engine/compute.ts).
- ADR-0008 (4 tabs + Otto circle): code has 5 tabs incl. `create` — [app/(tabs)/_layout.tsx:44-70](app/(tabs)/_layout.tsx) (ADR acknowledges "today's bar").
- ADR-0013 d1 (nutrition `~` with a range): single `kcal` value — [schemas.ts:13-29](src/features/nutrition/engine/schemas.ts).
- ADR-0013 d1 (vision names the dish): vision is transcription-only, declines non-recipe photos — [imageMode.ts:27-33](supabase/functions/generate-recipe/imageMode.ts).
- ADR-0013 d3 (ordered list with optional label): no label/position; `note='leftovers'` used as a tag — [plan.queries.ts:23](src/features/planner/plan.queries.ts), [PlanScreen.tsx:208](src/features/planner/PlanScreen.tsx).
- ADR-0013 d5 (3 scans before account): gate sends no-session users to auth only — [gate.ts:25](src/features/onboarding/gate.ts); all AI endpoints require a JWT; no DeviceCheck (grep).
- ADR-0014 (generated image, tagged): every generate mode returns `image: null`; no image model call exists (only Chat Completions, `_shared/openai.ts:5`, per C4).
- ADR-0007 (light only): consistent — `"userInterfaceStyle": "light"` — [app.json:8](app.json).
- ADR-0011: consistent per its own evidence (`app/_layout.tsx:29-51` per C4).
- Catalogue: ADR-0013/MAGIC_MOMENTS assume the 795-recipe catalogue, but the code default reads TheMealDB unless `EXPO_PUBLIC_USE_OTTO_RECIPES === 'true'` — [canonical.transform.ts:20-23](src/features/recipes/canonical.transform.ts); only `.env.development:9` sets it.

**Riskiest parts**
- Photo accuracy: the roadmap itself says 1.1 "can't ship on unmeasured accuracy" and needs a weighed calibration set — [PRODUCT_ROADMAP.md:164](docs/tickets/PRODUCT_ROADMAP.md); MAGIC_MOMENTS cites a documented ~1/3 calorie undercount for photo-only apps — [MAGIC_MOMENTS_V2.md](docs/product/MAGIC_MOMENTS_V2.md).
- Pre-account AI endpoint abuse: rate limiting is per isolate and resets on cold start — `_shared/http.ts:96-110` (EDGE_FUNCTIONS.md); MAGIC_MOMENTS warns it must not be abusable "the way `canonicalize` can today".
- Agent write authority: irreversible actions exist (delete recipe = hard delete, delete account, leave household) — [otto_actions_and_ai_today.md §1](docs/learning/research_notes/Otto%20AI%20agent%20research/otto_actions_and_ai_today.md); plan swap is non-atomic — [usePlan.ts:99-103](src/features/planner/usePlan.ts).
- Allergy safety in `plan_week`: prefs (and any allergies) are device-only today; roadmap makes "preferences on the account → week builder" the long pole — [PRODUCT_ROADMAP.md:86, 164](docs/tickets/PRODUCT_ROADMAP.md).
- Untested server handlers: "No test exercises the handler itself" — [EDGE_FUNCTIONS.md](docs/architecture/EDGE_FUNCTIONS.md); `verify_jwt` settings not in source control.
- SDK spike for NativeTabs/App Intents may fail — [PRODUCT_ROADMAP.md:173](docs/tickets/PRODUCT_ROADMAP.md).

### Inferences
- Flipping `REQUIRE_CLUB=on` and moving the rate limiter to Postgres should precede any new AI endpoint, otherwise the agent and scan paths inherit a client-only paywall and a resettable limit.
- The safest agent design reuses the review-first pattern already in the code (stage, then user confirms) for writes, with the `agent_actions` log for Undo; this keeps moment 3 within the honesty laws and App Review 1.2/5.1.2(i).

### Gaps
- Production values of `REQUIRE_CLUB` and the catalogue flag cannot be read from the repo.
- The live database may differ from migrations (the storage policy may "have been created by hand" — [ERD.md](docs/architecture/ERD.md)); not checked against the live project.
