# Close Otto's documentation gaps in the right order

A production app is "represented correctly" when about forty artifacts form one connected chain: **why we exist (vision, strategy, North Star) → which problem (jobs, opportunities) → what we build and what we don't (pitch or PRD with non-goals) → how it behaves (flows, statecharts, edge-case matrix, screen inventory) → how it looks and moves (tokens, components, motion) → how it is built (system overview, ADRs, data model, API contracts, threat model) → how we prove it (test strategy, acceptance criteria, fixtures, golden files) → how we ship and run it (release plan, flags, SLOs, runbooks, postmortems)**. Otto already has more of this chain than most one-founder apps: interactive flow maps with scenario lanes, a design-system spec plus code tokens guarded by a contrast test, eight module "contracts", 25 migrations as schema-as-code, a golden nutrition corpus, RLS attack tests, CI, store metadata traced to code, and a written multi-agent operating model ([otto_inventory](../research_notes/App%20documentation%20artifacts%20guide/otto_inventory.md)). The gaps cluster in three places. Formal decisions are missing (no ADRs). The run-time chain is missing (no crash reporting, analytics, SLOs, runbooks or postmortems). The user-centred product layer is missing (no personas, job stories, user research or North Star). Some docs that call themselves authoritative have also drifted from the code. `API_ARCHITECTURE.md` names Claude where the edge functions call OpenAI, and `contracts/database.md` lists "9 tables" without `otto_recipes`, `memberships` or `households` ([API_ARCHITECTURE.md](../../reference/API_ARCHITECTURE.md), [database.md](../../reference/contracts/database.md)). Because AI coding agents read these docs as law, stale docs are a live defect, not cosmetic debt. So the first job for a founder working with agents is to make the existing truth layer accurate and decisions explicit, before adding new artifact types.

## Seven layers form one chain, and every link needs one owner-artifact

The most useful idea in the research is that **no single document is the source of truth for everything**. Each type of decision has exactly one artifact that owns it, and every other artifact links to it instead of copying it. "Why we exist" lives in the vision and strategy. "What we measure" lives in the North Star and metric tree. "What's out of scope" lives in the pitch or PRD's non-goals. "How a complex component behaves" lives in a statechart plus an edge-case matrix. "What it looks like" lives in Figma frames marked Ready for dev plus tokens. "What actually shipped" lives in code and release notes. Figma itself offers only two official handoff statuses, "Ready for dev" and "Completed" ([Figma Help](https://help.figma.com/hc/en-us/articles/26781702258583-Dev-Mode-statuses-and-notifications)). That is one reason mature teams treat code-synced tokens, not the design file, as the final word on visuals once code exists.

Three cheap practices keep the chain from drifting. The first is **stable IDs**. Every screen (S-07), flow (F-03), edge case (E-12), requirement (REQ-PAY-03) and decision (ADR-0004) gets an ID that appears in Figma frame names, ticket titles, test names and code headers. Then a change to one link shows which other links must change. The second is **link, don't copy**: a PRD links to the Figma section and the statechart rather than pasting screenshots that go stale. The third is **make it executable where possible**. Statecharts drawn as diagrams drift from code unless they are executable ([wikidocs essay](https://wikidocs.net/blog/@jaehong/12380/)). Golden files and tests are specifications that cannot drift, which is why Gojko Adzic's "specification by example" lineage calls them living documentation.

For shelving all of this, **Diátaxis** is the dominant 2025–26 framework. It sorts documents by what the reader is trying to do, not by subject. Tutorials are for learning, how-to guides are for doing a task, reference is for looking things up, and explanation is for understanding why ([Semantic Anchors: Diátaxis](https://llm-coding.github.io/Semantic-Anchors/anchor/diataxis-framework)). Architecture overviews and design docs are explanation. API contracts, data dictionaries and token tables are reference. Runbooks are how-to. Otto's `docs/reference/contracts/` already follows the reference pattern. A `docs/decisions/` folder and a `docs/how-to/` folder for runbooks would complete it.

One correction matters throughout this report. Some of the general research examples assumed a SwiftUI client. Otto is an **Expo / React Native app** with expo-router routes (`(tabs)/` index, cookbook, create, plan, profile), a Supabase backend, RevenueCat for the "Otto Club" membership ($34.99/yr, $4.99/mo, 5-day trial), and OpenAI called only from edge functions ([README.md](../../../README.md), [app/](../../../app/)). Every Otto example below uses those real names.

UX artifacts describe behaviour, and the key distinction comes from NN/g. A **journey map** captures the user's actions, thoughts and feelings over time and across channels. A **user flow** captures in-product interactions: user actions and system responses ([NN/g](https://nngroup.com/articles/user-journeys-vs-user-flows)). For engineering precision the strongest artifact is the **statechart**. Harel introduced it in 1987 as a state machine with nested states, parallel regions and history ([Recurse Center](https://www.recurse.com/blog/59-paper-of-the-week-statecharts-a-visual-formalism-for-complex-systems)). It forces every state, including loading, error and waiting states, to be named, so missing unhappy paths surface by construction ([statecharts.github.io](https://redirect.github.com/statecharts/statecharts.github.io/blob/master/benefit-all-states-explored.md)).

## Design system: the law is written, the sign-offs are not

Apple HIG, Material 3, Polaris, Carbon, Atlassian and GOV.UK converge on one top-level shape. Principles come first, then voice, then foundations (colour, type, spacing, iconography, motion, haptics, accessibility), then tokens, components, patterns, and a changelog with a contribution model ([design_system notes](../research_notes/App%20documentation%20artifacts%20guide/design_system.md); [Atlassian](https://atlassian.design/foundations/content/voice-tone); [GOV.UK contribution criteria](https://design-system.service.gov.uk/community/contribution-criteria)). Here are the terms. A **design token** is a named design decision stored as data, for example `color.text.primary`. Tokens come in tiers. **Primitives** say what a value is (`color.terracotta.500`). **Semantics** say what it is for (`color.action.primary`). **Component tokens** say where it is used (`button.primary.background`). The interchange standard is now the **W3C DTCG format, first stable version 2025.10** (announced 28 Oct 2025), with Style Dictionary, Tokens Studio and Terrazzo as reference implementations ([W3C DTCG](https://www.w3.org/community/design-tokens/2025/10/28/design-tokens-specification-reaches-first-stable-version/)). Style Dictionary v5 adopted it as its base format ([zeroheight help](https://help.zeroheight.com/hc/en-us/articles/48049028236187)).

For a 1–3 person Expo team, the research is blunt about tooling. Figma Code Connect needs an Organization or Enterprise plan ([figma/code-connect](https://github.com/figma/code-connect/blob/main/cli/README.md)), and the Figma REST API does not return DTCG ([Figma forum](https://forum.figma.com/ask-the-community-7/native-variable-export-feature-47831)). The pragmatic path is to keep the repo's token file as the source of truth once code exists, to keep **Figma property names identical to TypeScript prop names**, and to test contrast on token values, because DOM-based axe checks do not apply to React Native ([Design Systems Collective](https://www.designsystemscollective.com/design-system-testing-visual-regression-accessibility-and-performance-in-ci-cd-3d612cbb266e)). Otto already does the hardest part: its contrast test and vocabulary guard turn design law into failing tests. The gap is governance. Six contracts still read "M0 draft" or "parity draft", and the motion maps await sign-off, although version 1.0.23 has shipped ([otto_inventory](../research_notes/App%20documentation%20artifacts%20guide/otto_inventory.md)). An agent cannot tell a draft that was abandoned from a draft that is de facto law.

## Architecture, data, API and security: authoritative docs have drifted from code

Here are the terms. A **design doc** (Google style) is written *before* coding a non-trivial change. It covers context and scope, goals and non-goals, the design, alternatives considered, and cross-cutting concerns such as security, privacy and monitoring ([Industrial Empathy](https://www.industrialempathy.com/posts/design-docs-at-google/)). An **RFC/RFD** wraps the same content in a review lifecycle. Oxide's states run prediscussion → ideation → discussion → published → committed ([Oxide RFD 1](https://rfd.shared.oxide.computer/rfd/0001)). That is overkill for one founder. An **ADR (Architecture Decision Record)** records one significant decision in a page. The MADR template orders it as title, status, context, decision drivers, considered options, outcome ("Chosen option: …, because …"), consequences, and confirmation (how compliance is checked) ([MADR reference](https://cdn.jsdelivr.net/npm/@harness-forge/cli@1.5.5/skills/madr-decision-log/references/madr-reference.md)). ADRs are never edited to reverse a decision. A new ADR supersedes the old one. **C4** draws architecture at four zoom levels: System Context, Container (separately runnable units such as the app, a database or an edge function, not Docker containers), Component, and Code ([Baeldung](https://www.baeldung.com/cs/c4-model-abstraction-levels)). **arc42** is a 12-section architecture-document skeleton whose §9 holds decisions and §11 holds risks and technical debt ([arc42 docs](https://docs.arc42.org/home/)). Mermaid renders sequence, state, ER and (since 11.1) `architecture-beta` diagrams directly in GitHub Markdown ([EventCatalog](https://eventcatalog.dev/docs/development/components/diagram-syntax/mermaid)).

Otto's strongest architecture artifact is not a document. It is the **migration folder as schema-as-code, plus an RLS attack test** in which user B tries create, read, update and delete on user A's rows across every table ([rls-attacks.test.mjs](../../../supabase/migrations/tests/rls-attacks.test.mjs)). That proves security behaviour instead of describing it. Its weakest point is that the prose around it has decayed. When `API_ARCHITECTURE.md` says the AI is Claude and the code says OpenAI, any agent planning a change to cost, privacy or prompt handling starts from a false map. A threat model matters especially for Otto because its stated security stance is unusual and deliberate: the anon key is committed because "RLS is the security boundary" ([keepalive.yml](../../../.github/workflows/keepalive.yml)). That stance is sound only if every trust boundary (device ↔ Supabase, edge function ↔ OpenAI, RevenueCat ↔ webhook) has been enumerated and tested.

## Specs and quality: Otto's golden tests are best-in-class, its E2E suite never runs

The specification terms sit at different levels, and they are easy to confuse. A **functional spec** says *what* users experience. A **technical spec** says *how* it is built. **Acceptance criteria (AC)** are pass/fail conditions for *one* story. The **Definition of Done** is the team-wide bar for *every* item. **BDD/Gherkin** writes AC as `Given / When / Then` examples that can be automated. **Example mapping** is a roughly 25-minute workshop with colour-coded cards: yellow for the story, blue for rules, green for examples, red for open questions. "The magic is in the conversation and not the colour of the cards" ([Cucumber](https://www.cucumber.io/docs/bdd/example-mapping)). Since 2025, **spec-driven development (SDD)** has meant structured Markdown specs that an AI agent works from. GitHub Spec Kit produces `spec.md`, `plan.md`, `tasks.md`, `data-model.md`, `contracts/` and `quickstart.md`, governed by a `constitution.md`. It forces agents to write `[NEEDS CLARIFICATION: …]` instead of guessing ([Spec Kit spec-driven.md](https://github.com/github/spec-kit/blob/main/spec-driven.md)). Kiro uses three files, with requirements written in EARS notation: `WHEN <trigger> THE SYSTEM SHALL <response>` ([Kiro](https://kiro.dev/docs/specs/concepts)). Birgitta Böckeler notes the definition of SDD "is still in flux" and ranks Kiro the lightest of the three tools she compared ([martinfowler.com](https://www.martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)). For Otto, a Kiro-weight spec per feature (requirements in EARS, design, tasks) fits the founder-plus-agents model. The full Spec Kit set is heavier than needed. Here is an Otto requirement line: "WHEN a user whose Otto Club membership has expired opens Ask Otto THE SYSTEM SHALL show the Otto Club sheet and not send the message."

A **test strategy** is the durable approach: which risks, at which layers, with which tools and gates. A **test plan** is per release: scope, schedule, devices, and entry and exit criteria ([imbus ISTQB glossary](https://www.imbus.de/en/glossar/term/test-strategy)). The pyramid ([Cohn via O'Reilly](https://www.oreilly.com/library/view/succeeding-with-agile/9780321660534/h4_419.html)), trophy and honeycomb ([Spotify](https://engineering.atspotify.com/2018/01/11/testing-of-microservices)) are heuristics for where to spend effort. For a React Native app that leans on a backend, the practical shape is a trophy. Static types and lint form the base. Integration tests (React Native Testing Library plus mocked network) form the bulk. A thin layer of **Maestro or Detox** end-to-end flows covers money and onboarding. Maestro is the common pick for Expo projects, although the speed figures in comparisons are vendor anecdotes ([helpmetest](https://helpmetest.com/blog/detox-vs-maestro/)).

Test data has precise names too. **Test double** is the umbrella term, and its kinds are dummy, fake, stub, spy and mock, as in Fowler's "Mocks Aren't Stubs" ([martinfowler.com](https://martinfowler.com/articles/mocksArentStubs.html)). A **fixture** is the known data a test starts from. A **factory** builds valid objects with overrides. A **seed** populates a whole environment's database. A **golden file / approval test** compares output against a human-approved recording ([Nicolas Carlo](https://dev.to/nicoespeon/what-s-the-difference-between-regression-tests-characterization-tests-and-approval-tests-2jf3)). A **test oracle** is the *source* of the expected answer ([softwaretestpilot](https://softwaretestpilot.com/istqb/glossary/test-oracle)). Subscriptions add three separate test environments. A local **StoreKit configuration file** can renew a subscription every few seconds without Apple's servers ([Apple](https://developer.apple.com/documentation/storekit/testing-in-app-purchases-in-xcode.md)). The **App Store sandbox** uses sandbox accounts on a device. **TestFlight** is the third. RevenueCat adds a Test Store, and StoreKit-file testing does not surface cancellation or refund events ([RevenueCat](https://www.revenuecat.com/docs/test-and-launch/sandbox/apple-app-store)).

|---|---|---|
| **Test strategy** (risk → lowest layer that catches it → tool → owner → gate) | "Membership gating is P0: unit test on the entitlement mapper, integration with mocked RevenueCat, StoreKit-file E2E, sandbox pass before every submission." | **Exists**: `TESTING.md` (L1 unit, L2 static, L3 browser journeys, L4 native) and `contracts/testing.md`; no ranked risk list |

Otto's quality story has one striking asymmetry. The nutrition engine is specified the way the best teams specify anything: golden corpus, oracle data and laws as tests. The **money path**, which a hard paywall turns into the app's single point of failure, is protected mainly by manual release tickets. One active ticket is literally an urgent fix for a RevenueCat purchase-transfer error ([TERMINAL_TICKET_PURCHASE_TRANSFER_FIX.md](../../tickets/TERMINAL_TICKET_PURCHASE_TRANSFER_FIX.md)). Treating the membership flow with the same rigour as nutrition, through a statechart, an edge-case matrix, a StoreKit file and running E2E, is the highest-value quality investment available.

## Delivery and operations: the observability chain is the biggest hole

Release mechanics on iOS have constraints that shape the artifacts. **Phased release** spreads an update over seven days (1, 2, 5, 10, 20, 50, 100%). It applies only to users with automatic updates, can be paused for up to 30 days in total, and cannot stop manual downloads ([Apple App Store Connect Help](https://developer.apple.com/help/app-store-connect/update-your-app/release-a-version-update-in-phases/)). TestFlight builds expire after 90 days ([Apple](https://www.developer.apple.com/help/app-store-connect/test-a-beta-version/testflight-overview)). Because a shipped binary cannot be recalled, **server-side feature flags are the real kill switch**, and a flag strategy (types, owner, expiry, default in binary) belongs next to the release plan. iOS also has two version fields: the marketing version (1.0.23) and the build number (52).

Operations artifacts come from Google SRE and PagerDuty. Here are the terms. An **SLI** is a measured ratio of good events to valid events. An **SLO** is the target for that ratio over a window. The **error budget** is the allowed failure. The **error budget policy** says what happens when the budget is spent: the canonical example freezes non-critical releases ([SRE Workbook Appendix B](https://sre.google/workbook/error-budget-policy/); [Real Python](https://realpython.com/ref/software-engineering-glossary/error-budget/)). A **runbook** is the procedure for one alert. An **incident plan** defines severities and roles; PagerDuty's "command staff" are Incident Commander, Deputy and Scribe ([PagerDuty](https://response.pagerduty.com/training/glossary/)). A **blameless postmortem** analyses failed systems and processes rather than people ([Jacar](https://jacar.es/en/the-site-reliability-workbook-patterns-we-still-use/)). On iOS, the observability signals are launch time to first draw and hang rate, where a hang is the UI being unresponsive for at least 250 ms ([Apple](https://developer.apple.com/documentation/xcode/reducing-your-app-s-launch-time.md); [WWDC21 notes](https://www.wwdcnotes.com/notes/wwdc21/10181)). Crash data comes from MetricKit, which delivers reports at most daily ([NSHipster](https://nshipster.com/metrickit)), or from a crash SDK. A **tracking plan** specifies analytics events in object-action form ("Recipe Saved"), with typed properties, triggers and owners ([Amplitude](https://amplitude.com/blog/analytics-tracking-practices)). **DORA** now has five delivery metrics after adding deployment rework rate in 2024 ([CD Foundation](https://cd.foundation/blog/2025/10/16/dora-5-metrics/)). Its 2025 report finds AI is an amplifier and that AI adoption is associated with higher instability ([Google blog](https://blog.google/technology/developers/dora-report-2025/)). That warning applies directly to a founder shipping through agents.

The ticket-as-handoff model is efficient. Git carries tickets between a cloud session without Apple credentials and a terminal session on the founder's Mac ([tickets SKILL.md](../../../.claude/skills/tickets/SKILL.md)). The cost is that tickets double as backlog, release checklist and incident record, and they get archived. As a result, no durable artifact owns "how we release", "what happened in incident X" or "why we decided Y". For a live subscription app, the missing **observability chain is the most consequential gap**. Without crash reporting or purchase-success signals, the founder learns about a lockout from App Store reviews, not from an alert.

## Four hats, one founder: who owns, writes and reviews what

The research found no published cross-role sign-off matrix, so the assignments below are a synthesis grounded in role definitions. Larson's Staff+ archetypes (Tech Lead, Architect, Solver, Right Hand) and Reilly's three pillars (big-picture thinking, project execution, levelling up others) define the **principal engineer** as the owner of technical direction and the quality of decisions ([Lebrero notes](https://danlebrero.com/2022/02/23/staff-engineering-leadership-beyond-the-management-track-book-summary/); [O'Reilly](https://oreilly.com/library/view/the-staff-engineers/9781098118723/preface01.html)). The **technical director** (a small-company CTO) owns strategy, risk, reliability and release go/no-go. Fournier herself started as "a director of engineering in name and something closer to a tech lead in practice" ([O'Reilly](https://www.oreilly.com/library/view/the-managers-path/9781491973882/preface02.html)). In games, a technical director aligns engineering with creative ambitions ([PlayStation careers](https://careers.playstation.com/studio-technical-director/job/6102828004)). The **creative director** owns brand vision and the creative concept, while a design director owns execution quality and consistency ([Wikipedia](https://en.wikipedia.org/wiki/Design_director)). The **technical creative director** is the bridge: feasibility and craft of motion, assets and pipelines ([Yardstick](https://yardstick.team/job-description/creative-technology-director); [EA posting](https://hitmarker.net/jobs/electronic-arts-technical-art-director-902329)). In the table, **A** means approves or is accountable, **W** writes, and **R** reviews.

For Otto, all four hats sit on one head, and AI agents are the team. The practical consequence is that the founder's job shifts from producing artifacts to **approving them**. Agents can draft almost every row: ADRs from the decision log, ERDs from migrations, contracts from function code, changelogs from commits. Agents cannot supply the judgment cells: strategy, brand intent, risk acceptance, go/no-go. Those must be recorded as signed decisions, or agents will re-litigate them. The `otto-lead` skill's "do not re-litigate" lines show the founder already feels this need ([otto-lead SKILL.md](../../../.claude/skills/otto-lead/SKILL.md)).

## What to add first: a ten-step order for a founder with agents

The order below rests on three judgments. Accuracy of what agents already read beats new coverage. Protecting the hard-paywall money path beats everything else in a live subscription app. User-centred product work matters most, but its payoff is slower. Each step reuses material already in the repo.

| # | Add or fix | Why now | Source material already in Otto |
|---|---|---|---|
| 1 | **Root `CLAUDE.md` + doc-freshness convention** ("Status · Last verified at commit SHA"), fix `docs/README.md`, move `reference/bagged/` out, mark superseded docs, fix `README.md`'s Otto Club line (it still says $34.99/yr and a 5-day trial; the store and the app's fallback copy are $39.99/yr, 7-day trial) | Agents load stale law today; this is the cheapest fix with the widest effect | `CONTEXT_ENGINEERING.md`, ticket 00, `otto-lead`; SHA-pinning already used in `OTTO_GAP_AUDIT.md` |

A reasonable objection is that step 9 belongs first, because a product built on intuition can be precisely documented and still wrong. That holds for a pre-launch app. Otto is live with paying members, though, and there the cost of a lockout or a stale agent map lands this week, while research changes decisions over months. The order also deliberately skips heavyweight forms the research flags as overkill at this size: full RFC processes, ATAM workshops, RACI charts, release trains and the full Spec Kit artifact set.

## Conclusion

The real gap at Otto is not a lack of documents. **Its documents lack an authority model.** The repo has roughly 391 docs, but it does not record which one is current, who signed it, or at what commit it was last verified. In a team of humans, stale docs are ignored. In a team of agents, they are executed. That changes the priorities. The most valuable artifacts for a founder working with AI agents are the ones that turn judgment into durable, checkable constraints: ADRs for decisions, generated ERDs and contracts for the system, statecharts and golden files for behaviour, and SLOs for run-time health. Otto's own best work already proves the pattern. Its nutrition laws, contrast test, vocabulary guard and RLS attack test are documentation that fails a build when it stops being true.

The second takeaway is that the four leadership roles converge on one discipline when a single person holds them. The principal engineer and the technical creative director write the specs, the technical director and creative director approve them, and agents draft the rest. The founder therefore needs fewer new documents than the golden-standard catalogue suggests, and needs to be stricter about status, sign-off and links between the ones that exist. Done in the order above, the first three steps take days rather than weeks and use material already in the repo. They also make every later artifact cheaper, because each one can then link to a trustworthy foundation instead of contradicting it.
